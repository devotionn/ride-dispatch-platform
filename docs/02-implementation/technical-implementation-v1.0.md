# 技术实施与现实落地方案 V1.0

- 状态：BASELINE（技术方向）
- 适用基线：PRD V1.3
- 目标：在约 300 名司机以内的现实车队环境中，以最小必要复杂度实现稳定、可审计、可扩展的调度系统。

## 1. 总体判断

本项目的主要难点不是高并发，而是业务一致性：

- 订单不能被取消和接单同时成功；
- 旧派单尝试不能在改派后再次生效；
- 支付回调重复不能重复记收入；
- 线下已收款不能再次进入平台可提现余额；
- 提现申请、审核、驳回、打款必须可对账；
- 强制改派、强制取消、金额修正必须完整审计。

因此优先级是：**事务、幂等、约束、审计、备份 > 分布式组件和架构炫技**。

## 2. 推荐技术架构

```text
Internet
   │
 HTTPS
   │
 Nginx
   ├──────── passenger-h5
   ├──────── admin-web
   └──────── /api
              │
        Spring Boot
              │
           MySQL
```

司机 Android App 通过 HTTPS API 与实时通知通道访问同一后端。

### 2.1 后端

推荐：

- Java 21 LTS
- Spring Boot 4.x（使用项目启动时的受支持稳定版本）
- Spring Security
- Spring Data JPA 或明确可控的数据访问层
- Flyway
- MySQL 8.x

### 2.2 Web

- Vue 3
- TypeScript
- Vite
- 乘客 H5：Vant
- 管理后台：Element Plus

### 2.3 Android

- Kotlin
- Jetpack Compose
- Android 原生通知
- 位置前台服务（实际版本权限策略按目标 Android SDK 验证）
- 推送 Provider 抽象

### 2.4 首期明确不需要

- Spring Cloud 微服务
- Kafka / RabbitMQ
- Elasticsearch
- Redis Cluster
- Kubernetes
- 独立 API Gateway

Redis 是否需要以后由实际缓存、分布式锁或会话需求决定，不作为起步依赖。

## 3. 模块化单体

建议后端包/模块：

```text
server/
├─ auth/
├─ brand/
├─ driver/
├─ order/
├─ dispatch/
├─ payment/
├─ settlement/
├─ withdrawal/
├─ audit/
├─ notification/
└─ shared/
```

### 3.1 模块职责

- `auth`：后台和司机身份认证、角色权限。
- `brand`：公司名称和 Logo 配置。
- `driver`：司机、车辆、接单状态、当前可接人数、当前位置。
- `order`：订单创建、状态、乘客访问令牌、履约阶段。
- `dispatch`：附近司机、派单尝试、接受、拒绝、改派。
- `payment`：应收款、支付尝试、第三方回调、线下收款、修正。
- `settlement`：司机业务收入、可提现余额和资金流水。
- `withdrawal`：提现申请、冻结、审核、驳回和人工打款。
- `audit`：高权限操作审计。
- `notification`：司机新单通知、实时消息和推送抽象。

模块之间通过明确应用服务调用，不允许前端直接拼业务状态。

## 4. 核心业务一致性策略

### 4.1 订单写操作必须在服务端校验当前状态

客户端提交“接受订单”只代表请求，最终是否成功由服务器根据数据库当前状态决定。

### 4.2 并发控制

核心对象建议带 `version` 乐观锁字段。以下场景必须有并发自动化测试：

- 乘客取消 vs 司机接受；
- 调度员改派 vs 原司机接受；
- 两名后台人员同时派单；
- 重复支付回调；
- 两次同时提现申请。

对个别必须串行化的短事务，可使用数据库行锁，但禁止用长事务包住网络调用。

### 4.3 第三方调用不放在数据库长事务中

例如支付创建、推送、文件上传应遵循：

```text
本地落状态/生成任务
→ 提交事务
→ 调用外部系统
→ 记录结果或进行补偿
```

## 5. 订单与调度

PRD V1.3 的用户可见主状态继续作为权威业务状态：

`PENDING_DISPATCH → PENDING_DRIVER_CONFIRM → ACCEPTED → IN_SERVICE → PENDING_PAYMENT → COMPLETED`

并允许按规则进入 `CANCELLED` / `EXCEPTION`。

每次派单、拒单、改派都必须建立独立 `DispatchAttempt`，不能只覆盖 `orders.current_driver_id`。

### 5.1 当前司机与目标司机

实现时应区分：

- 来源司机：订单由谁的专属二维码带来；
- 当前负责司机：当前实际负责履约的人；
- 某一次派单的目标司机：保存在 DispatchAttempt。

从而避免司机二维码来源统计被改派覆盖。

## 6. 附近司机

PRD V1.3 条件：

- 订单 A 点为中心；
- 10km；
- 司机账号正常；
- 可接单；
- 定位 ≤ 5 分钟；
- 当前可接人数满足；
- 直线距离升序；
- 人工选择。

约 300 名司机规模下使用 MySQL 存当前经纬度并计算球面距离即可。不要把“直线距离”显示成“预计到达时间”。

## 7. 地址输入和坐标

乘客 H5 使用浏览器原生定位、系统维护的 Place Catalog 搜索和手工地址输入；司机 App 负责定位上报。坐标是可选信息，未获得坐标时仍可创建订单并由后台人工派单。

实施原则：

- 同一业务链路统一坐标体系；
- 地址文字始终保存，经纬度按可用性保存；
- 当前司机位置带 `located_at`，不能只依赖数据库更新时间；
- 位置有效性由服务端计算；
- PRD 首期不展示实时轨迹，不代表后续生产运营不能保留必要的合规/审计位置记录。

当前实现不集成 AMap、Baidu、Tencent 等商业地图 SDK，不读取地图 Key，也不需要地图服务代理。

## 8. Android 现实环境

### 8.1 定位

“超过 5 分钟无定位视为失效”是有效性阈值，不代表只能每 5 分钟上传一次。

上传周期应配置化，并在真机功耗、定位质量和调度实时性之间验证。

### 8.2 新单通知

不把 WebSocket 当作唯一可靠通道。

建议：

```text
NotificationService
├─ RealtimeChannel
└─ PushProvider
```

App 前台/活跃时可实时刷新；后台/锁屏依赖系统通知和 Push Provider。

### 8.3 弱网

- 订单详情可本地缓存用于查看。
- 定位可在短暂断网后恢复上传。
- 接单、拒单、履约状态、收款等关键操作必须服务端确认成功后 UI 才显示成功。

## 9. 乘客 H5 安全

乘客无复杂账号体系是 V1.3 的明确选择。

因此实现时建议：

- 订单创建成功后生成不可预测 `passengerAccessToken`；
- 查询/取消使用 Token，而不是可枚举自增 ID；
- 司机二维码使用 `driverShortCode`，不暴露数据库 ID；
- 下单接口支持 `Idempotency-Key` 防重复点击；
- 公共 H5 增加合理限频，异常流量再触发额外验证。

这些属于实现安全措施，不改变“无需短信验证码”的产品要求。

## 10. 支付

### 10.1 模型

建议：

```text
Order
  └─ Payment（订单应收）
       └─ PaymentAttempt[]（一次或多次支付尝试）
```

一个订单可能先微信取消、再支付宝成功，因此不能把第三方支付记录硬设计成 1:1。

### 10.2 支付 Provider

```text
PaymentProvider
├─ MockPaymentProvider
├─ WeChatPayProvider
└─ AlipayProvider
```

先用 Mock 打通闭环，真实商户资料确认后替换 Provider。

### 10.3 成功判定

- 服务端回调验签；
- 校验商户、订单、金额和状态；
- 回调幂等；
- 必要时支持主动查询补偿；
- 第三方流水号建立唯一约束；
- 前端支付结果页不是最终账务依据。

## 11. 资金与提现

必须区分：

- 司机业务收入：该订单产生了多少收入；
- 平台可提现余额：目前仍由平台代持、可申请结算给司机的钱。

### 11.1 线上公司商户收款

订单收入进入业务收入，同时按确认后的结算规则增加可提现余额。

### 11.2 司机已直接线下收款

订单收入进入业务收入统计，但默认不得再次增加平台可提现余额，否则会产生重复支付风险。

该规则属于关键实施规则，应在 PRD V1.4 讨论中正式确认。

### 11.3 账户

建议：

```text
DriverAccount
- available_balance
- frozen_balance
```

提现申请时从 available 转 frozen；驳回时解冻；实际打款完成时核销 frozen。

所有资金变化都追加 `DriverLedger`，禁止仅修改余额而没有流水。

金额统一以最小货币单位整数存储，禁止使用浮点数记账。

## 12. 审计

以下动作必须在同一业务事务内写 `OperationLog`：

- 执行中强制改派；
- 已接单/执行中强制取消；
- 线下收款修正；
- 提现审核/驳回；
- 人工打款确认；
- 关键系统配置修改。

审计至少包含操作者、对象、动作、前值、后值、原因、时间。

## 13. 权限

首期使用简单 RBAC 即可：

- ADMIN：系统与业务全权限；
- DISPATCHER：司机、订单、派单、异常处理；
- FINANCE：支付、收入、提现、财务修正；

关键权限在服务端鉴权，不能只隐藏前端按钮。

## 14. 文件与品牌资源

品牌 Logo 使用 `StorageService` 抽象。

开发环境可本地文件；生产可切换对象存储。不把文件路径写死进业务逻辑。

## 15. 部署原则

### 开发/测试

Docker Compose 可以运行 Nginx、Spring Boot、MySQL。

### 生产

推荐最小结构：

```text
Nginx / HTTPS
   ↓
Spring Boot
   ↓
Managed MySQL 或具备可靠备份的 MySQL
```

另配对象存储、日志和数据库备份。约 300 司机不需要 Kubernetes。

## 16. 可扩展点

以下能力只预留接口，不在信息不足时盲写：

- `PushProvider`
- `PaymentProvider`
- `MapProvider`
- `StorageService`
- `RegulatoryReportService`

## 17. 实施底线

- 不用数据库状态覆盖历史事实。
- 不用前端状态代替服务端业务判断。
- 不用浮点数处理资金。
- 不让重复回调产生重复收入。
- 不让线下已收款再次提现。
- 不让重要后台操作无审计。
- 不在未明确实际商户/运营关系前写死资金结算模型。
- 不为了 300 司机规模提前引入分布式复杂度。
