# 测试与验收策略 V1.0

- 状态：DRAFT
- 目标：不仅证明页面能点，更证明订单、支付、余额和异常操作在真实并发/弱网环境中不会乱。

## 1. 测试层级

1. 单元测试：状态规则、金额计算、权限判断。
2. Repository/数据库集成测试：唯一约束、锁、事务、Flyway。
3. API 集成测试：真实 Spring Context + MySQL 测试实例。
4. 前后端 E2E：关键闭环。
5. Android 真机测试：通知、后台定位、弱网。
6. UAT：调度员、司机、财务按现实流程操作。
7. 生产前小规模灰度。

## 2. PRD V1.3 乘客验收映射

### P-H5-001 公共入口

- `/ride` 可直接访问；
- 不要求 driverShortCode；
- 提交后为待接单。

### P-H5-002 司机定向入口

- 正确短码识别司机；
- 页面锁定司机；
- 提交后待司机确认；
- 司机拒绝后订单转待接单。

### P-H5-003 A 点定位

- 允许定位时默认填充；
- 拒绝权限仍能手工输入；
- 自动定位后仍可修改。

### P-H5-004 无短信验证码

- 合法手机号格式可直接创建；
- 不依赖短信服务。

### P-H5-005 取消

- 接单前可取消；
- 接单后乘客取消接口拒绝。

### P-H5-006 订单付款二维码

- 与司机下单二维码不同；
- 绑定订单和金额；
- 支付结果由服务端结果决定。

## 3. 司机 App 验收

### D-001 品牌

后台更换品牌配置后，司机端重新加载可看到变化，无需重新发 APK。

### D-002 二维码

- 长期短码稳定；
- 正确打开 H5；
- 不可作为支付二维码。

### D-003 定位时效

- locatedAt ≤5 分钟：满足其他条件时可进入附近候选；
- >5 分钟：必须被附近候选排除；
- 全部司机视图可提示位置失效。

### D-004 新单提醒

- App 前台；
- App 后台；
- 锁屏；
- 系统省电策略下；
- Push 到达时；
- 实时通道断开时。

至少覆盖主流实际司机机型/厂商组合。

### D-005 接受/拒绝

- 接受成功后订单已接单；
- 拒绝必填原因；
- 拒绝后待接单；
- 已失效 Attempt 不能接受。

### D-006 多订单

- 同一司机可存在多个订单；
- 列表和详情不相互覆盖；
- 每个订单履约进度独立。

### D-007 履约顺序

按到达出发地 → 接到乘客 → 行程中 → 到达目的地推进；非法倒退/跳跃被拒绝。

### D-008 收款/提现

Mock 支付阶段也必须完整跑通账户和提现状态机。

## 4. 后台验收

- 三种来源可筛选。
- 后台可代客创建。
- 附近司机严格应用 10km、位置时效、接单状态、人数，并按直线距离排序。
- 10km 无候选时仍可进入全部可接司机。
- 派单后显示等待时长，不自动改派。
- 强制改派/取消要求二次确认、原因和日志。
- 线下收款修正保存前后值。
- 提现审核、驳回、待打款、已打款可闭环。

## 5. 必测并发场景

### C-001 乘客取消 vs 司机接受

同时发起，最终只能出现一个合法结果。失败方拿到明确状态冲突，不允许数据库出现“已取消但司机已接单”的混合状态。

### C-002 改派 vs 原司机接受

改派一旦先成功，原 Attempt 后续接受失败。

### C-003 两个调度员同时派同一订单

不能产生两个同时有效的 WAITING Attempt。

### C-004 两次提现

余额只够一次时，两次并发申请只能一次成功。

## 6. 支付/资金必测不变量

### F-001 重复回调

同一成功回调执行 10 次：

- Payment 仍只成功一次；
- DriverLedger 只生成一次对应收入；
- 可提现余额只增加一次。

### F-002 不同支付尝试

微信失败/取消后支付宝成功，订单最终只按支付宝成功一次结算。

### F-003 金额不一致

回调金额与本地应收不一致时不能直接入账，进入异常处理。

### F-004 线下收款

司机直接线下收 100：

- 业务收入 +100；
- 若按实施规则确认，平台可提现 +0。

### F-005 提现冻结

申请 300：available -300, frozen +300；驳回恢复；已打款只核销 frozen。

### F-006 人工修正

修改前后金额和操作原因都可在审计中还原。

## 7. 幂等测试

对每个要求幂等的写接口：

- 同 key 同请求重复 2/10/100 次；
- 超时后重试；
- 同 key 不同 body；
- 多节点（未来如果有）一致性。

预期：不产生重复业务实体或资金流水。

## 8. 弱网测试

Android：

- 2G/高延迟模拟；
- 请求发出后断网；
- 服务端已成功但客户端超时；
- 网络恢复重试；
- 重复点击。

关键动作必须通过幂等和重新拉取状态恢复。

## 9. 权限测试

- Dispatcher 不能执行未授权财务动作；
- Finance 不能直接强制改派；
- Driver A 不能读取/操作 Driver B 的订单；
- Passenger Token A 不能读取订单 B；
- 禁用司机不能继续接新单。

## 10. 审计测试

对每项强权限操作验证：

- 操作成功必有 OperationLog；
- 业务事务失败不得残留“成功”审计；
- before/after、reason、operator、time 完整；
- 敏感字段被脱敏。

## 11. 数据库恢复测试

上线前至少完成一次：

```text
创建测试订单/支付/账本数据
→ 备份
→ 删除/破坏测试库
→ 从备份恢复到独立实例
→ 核对订单、Ledger、Withdrawal
```

没有验证过恢复的备份不能算可靠备份。

## 12. 灰度验证

推荐：

```text
内部开发数据
→ 3~5 名真实司机
→ 10~20 名司机
→ 50 名司机
→ 全量
```

每阶段记录：通知到达率、定位时效、派单耗时、异常单、重复单、支付差异和司机反馈。

## 13. Release Gate

一个阶段可封板至少满足：

- 对应 PRD 验收用例 PASS；
- 核心自动化 PASS；
- 无未解释的数据一致性失败；
- 数据库迁移可重复执行；
- 关键日志/审计可查；
- 已知风险有明确文档，不用“暂时没遇到”代替结论。
