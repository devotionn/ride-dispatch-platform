# PRD V1.4 待确认与建议调整项

- 状态：PROPOSAL
- 重要：本文件不是现行 PRD，不得把以下建议当作已经确认的甲方需求。
- 目的：把 V1.3 在现实实施中暴露出的歧义集中管理，确认后再正式形成 PRD V1.4。

## 2026-08-23 实施边界记录

Phase 2 浏览器 Gate 已通过，但不改变本文件的 `PROPOSAL` 状态。当前代码已经采用以下保守实现，作为技术实现事实，不等于业务已经确认：

- CHANGE-002：强制改派等待新司机确认期间保留原司机责任；
- CHANGE-004：使用不可预测 PassengerAccessToken 访问订单；
- CHANGE-005：使用 `Idempotency-Key` 防止弱网重复下单；
- 相关并发、越权和幂等测试已加入后端测试，但正式 PRD、领域、数据、API 文档仍需业务确认后统一升级。

进入真实支付/提现前，CHANGE-003、006、010、011、020 仍是硬性决策门槛；不能因为 Phase 2 通过就直接开发真实渠道或结算余额。

## PRD-CHANGE-001 — 立即单与预约单语义

- 优先级：P1
- V1.3：要求乘客填写“出发时间”，附近司机统一按 A 点 10km 当前位置筛选。
- 现实问题：预约几个小时/几天后的订单，司机“当前距离”与实际出发时的位置可能无关。
- 建议：明确 `IMMEDIATE / SCHEDULED`；立即单继续按当前 10km 筛选，预约单增加时间冲突/已有预约展示，当前距离只作为参考或按甲方规则使用。
- 需要确认：是否真的存在预约未来时间的业务；预约提前多久；是否仍强制 10km。

## PRD-CHANGE-002 — 执行中强制改派的责任交接

- 优先级：P0
- V1.3：执行中允许强制改派。
- 歧义：新司机尚未接受时，原司机是否立即失去订单。
- 建议：新司机接受并完成交接前，原 currentDriver 保持不变；失败时原订单继续由原司机负责。
- 原因：现实中乘客可能已经上车。

## PRD-CHANGE-003 — 线下收款与可提现余额

- 优先级：P0
- V1.3：支持线下收款，同时有司机收入和提现。
- 风险：司机已经直接拿到现金/个人收款，如果系统又把同一金额计入平台可提现余额，会重复给钱。
- 建议：线下直接收款计入业务收入，但 withdrawableDelta=0；只有实际由甲方商户代收、需后续结算给司机的金额才进入可提现余额。
- 需要甲方财务确认实际资金关系。

## PRD-CHANGE-004 — 乘客订单访问方式

- 优先级：P0
- V1.3：不做短信验证码/复杂账号，但需要订单状态和取消。
- 歧义：乘客如何安全找回/访问订单。
- 建议：创建订单返回不可预测 PassengerAccessToken；浏览器保存；无需注册。
- 补充：丢失访问链接时可联系后台人工查询。

## PRD-CHANGE-005 — 订单重复提交防护

- 优先级：P0
- V1.3：未定义。
- 现实问题：手机弱网和连续点击可创建重复订单。
- 建议：客户端 requestId / Idempotency-Key；服务端同 key 不重复创建。

## PRD-CHANGE-006 — 支付允许多次尝试但只能结算一次

- 优先级：P0
- V1.3：描述微信/支付宝支付成功，但未定义一次失败后换渠道。
- 建议：一个订单应收 Payment，可存在多个 PaymentAttempt；最终只能一个成功结算；第三方回调幂等。

## PRD-CHANGE-007 — 线上与线下“收入”展示口径

- 优先级：P1
- 问题：司机可能看到“总业务收入”和“可提现余额”不同。
- 建议：司机端明确区分：
  - 订单业务收入；
  - 平台代收待结算；
  - 已直接线下收款；
  - 可提现；
  - 提现冻结。
- 避免司机误解“为什么完成 100 元订单但余额没 +100”。

## PRD-CHANGE-008 — 司机接单后临时无法履约

- 优先级：P1
- V1.3：定义拒绝发生在接单前，但未定义司机接受后临时故障/无法履约。
- 建议：司机不能自行无痕取消；提供“联系调度/申请异常”，后台执行改派或取消并记录原因。

## PRD-CHANGE-009 — 乘客接单后修改 A/B 点

- 优先级：P1
- V1.3：未定义。
- 建议候选：乘客接单后不能直接修改；由后台在与司机确认后进行受控变更并留操作记录。
- 需要确认是否现实中经常临时改地址。

## PRD-CHANGE-010 — 最终金额的锁定规则

- 优先级：P0
- V1.3：司机收款前录入最终金额，后台可修正线下记录。
- 建议：生成线上付款上下文后金额变更必须使旧付款上下文失效或重新生成；支付成功后不能直接覆盖成功金额，只能走退款/人工差异处理。

## PRD-CHANGE-011 — 提现冻结余额

- 优先级：P0
- V1.3：提现有待审核、待打款、已打款/驳回。
- 建议：申请时从 available 转 frozen；驳回解冻；打款后核销 frozen。
- 原因：否则同一余额可在等待审核时重复申请。

## PRD-CHANGE-012 — 司机定位上传频率

- 优先级：P1
- V1.3：只规定超过 5 分钟失效，没有规定上传周期。
- 建议：上传周期后台/配置层可调，在真机功耗和实时性测试后确定；5 分钟继续作为产品失效阈值。

## PRD-CHANGE-013 — 司机当前可接人数的含义

- 优先级：P1
- V1.3：司机手工维护当前可接人数，同时允许多订单并存。
- 歧义：系统是否自动因已接订单扣减；司机是否仍可手工覆盖。
- 建议：首期保持“司机手工维护”为权威，系统展示现有订单人数作为风险提示，不自行推断顺路和实际剩余座位。
- 原因：V1.3 明确顺路由司机自己判断。

## PRD-CHANGE-014 — 预约单提醒

- 优先级：P1
- 现实需求候选：后台应该突出即将出发但仍待接单/待司机确认的订单。
- 建议：只提醒，不自动派单。
- 待确认：提前多少分钟进入高优先级提醒。

## PRD-CHANGE-015 — 支付日常对账

- 优先级：P2
- V1.3：只定义回调为准。
- 建议：真实支付上线后增加支付平台交易与本地 Payment 的日常对账/差异列表。
- 目的：处理漏回调、异常状态和人工查账。

## PRD-CHANGE-016 — 生产发票/投诉能力

- 优先级：P2
- V1.3：发票、评价属于首期不做。
- 现实问题：正式运营模式可能对票据、投诉处理等有额外要求。
- 建议：开发首期不扩展营销功能，但生产上线前由甲方确认实际经营资质和监管要求；如果需要，先做最小人工申请/后台处理流程，而不是复杂营销系统。

## PRD-CHANGE-017 — 司机/车辆资质字段与监管接口

- 优先级：P2
- 建议：数据库模型预留司机/车辆资质信息和 RegulatoryReportService Adapter，但在本地监管协议、甲方运营模式未确认前不写死上报实现。

## PRD-CHANGE-018 — 运营位置历史

- 优先级：P2
- V1.3：首期不做“实时轨迹”。
- 需要区分：不展示实时轨迹 vs 是否需要保存必要运营/审计位置记录。
- 建议：生产上线前由业务/合规确认保存粒度、期限和用途，技术上将 Current Location 与 History 分离。

## PRD-CHANGE-019 — 退款人工流程细化

- 优先级：P2
- V1.3：不做自动退款，进入人工异常。
- 建议明确最小字段：原支付流水、退款原因、申请人、处理人、退款金额、外部退款凭证、完成时间；即使不调用自动退款 API，也必须可追溯。

## PRD-CHANGE-020 — 真实支付商户与司机结算关系

- 优先级：P0（真实支付开发前必须确认）
- 当前设想：乘客付款到甲方商户账户，系统再记司机收入并人工提现。
- 必须确认：谁是交易收款主体、谁向乘客提供票据、司机结算属于什么业务关系、支付服务商支持什么模式。
- 技术要求：Payment 与 DriverSettlement 解耦，在确认前不把某一种资金法律/会计关系写死进 Order。
