## A. 业务经营模式

- [ ] 甲方确认系统实际用于哪类客运/预约接送业务。
- [ ] 确认是否涉及需要特定经营许可/司机资质/车辆资质的运营形态。
- [ ] 确认平台、车队、司机之间的合同和责任关系。
- [ ] 确认执行中改派、司机临时故障、乘客临时改地址的实际 SOP。
- [ ] 确认预约订单的真实业务规则。

## B. 支付与财务

- [ ] 确认微信/支付宝实际商户主体。
- [ ] 确认谁是乘客交易收款主体。
- [ ] 确认司机收入的结算性质和财务口径。
- [ ] 确认线下现金/个人收款是否允许及统计方式。
- [ ] 确认线下已收款不重复进入可提现余额的规则。
- [ ] 确认提现收款信息类型和人工打款 SOP。
- [ ] 确认 T+3 是自然日还是工作日及起算点。
- [ ] 明确支付差异、漏回调和退款的人工处理人。
- [ ] 上线真实支付前完成沙箱/测试商户验证。
- [ ] 上线真实支付前完成重复回调、金额不一致和主动查询测试。
- [ ] 建立支付对账流程。

## C. 票据、投诉与客服

- [ ] 确认正式业务是否要求票据/发票能力。
- [ ] 如果需要，明确首期采用自动还是人工开票流程。
- [ ] 明确投诉/异常单的登记、负责人、处理结果和留痕。
- [ ] 建立乘客无法访问订单时的人工查询流程。

## N. 上线后的第一批指标

不追求复杂 BI，先看：

- 新建订单数；
- 待接单积压和等待时间；
- 待司机确认时间；
- 拒单次数/原因；
- 定位失效司机数；
- 新单通知失败；
- 订单取消/异常率；
- 支付成功/异常；
- Payment 与 Ledger 差异；
- 提现积压；
- 调度员人工处理耗时。

只有这些基础指标稳定后，再考虑更复杂的运营分析。
