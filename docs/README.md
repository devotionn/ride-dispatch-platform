# 项目文档中心

## 1. 文档目的

本目录用于统一管理 Ride Dispatch Platform 的产品、技术、数据、接口、测试、部署、路线和生产上线文档。

文档体系必须解决三件事：

1. 团队清楚 **甲方已经确认了什么**；
2. 开发清楚 **应该如何实现**；
3. 发现现实问题时清楚 **哪些必须再次确认，不能自行修改需求**。

## 2. 文档状态定义

| 状态 | 含义 |
| --- | --- |
| BASELINE | 已作为当前开发依据 |
| DRAFT | 可用于讨论和实现准备，但仍可能调整 |
| PROPOSAL | 建议项，未得到业务确认 |
| SUPERSEDED | 已被新版本替代，仅保留历史 |

## 5. 需求与技术边界

### PRD 负责回答

- 谁使用；
- 做什么；
- 页面和流程是什么；
- 用户可以/不可以做什么；
- 首期范围是什么；
- 验收结果是什么。

### 技术实施文档负责回答

- 如何拆模块；
- 如何存数据；
- 如何处理事务和并发；
- 如何保证支付/资金幂等；
- 如何应对 Android、弱网、部署和备份；
- 如何为尚未确认的生产要求预留扩展点。

技术文档不得自行把 PROPOSAL 变成 BASELINE 产品需求。

## 6. 变更流程

发现需求缺口或现实冲突时：

```text
发现问题
  ↓
写入 PRD-V1.4-change-proposals.md
  ↓
说明当前 V1.3 规则、现实问题、建议规则和影响
  ↓
业务/甲方确认
  ↓
形成新的 PRD 版本
  ↓
同步技术、数据、API、测试文档
```

## 7. 文档更新约束

- 所有金额规则必须同步检查 Payment、DriverAccount、DriverLedger、Withdrawal 和测试文档。
- 所有订单状态变化必须同步检查状态机、API、数据库约束和测试用例。
- 所有司机定位规则必须同步检查 Android、附近司机查询、数据模型和生产隐私说明。
- 所有支付规则必须同时检查回调幂等、第三方流水、对账和异常处理。
- 所有强权限操作必须检查二次确认、原因和 OperationLog。
